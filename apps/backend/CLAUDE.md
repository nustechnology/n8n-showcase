# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NestJS + Prisma + PostgreSQL backend for a multi-tenant order automation platform. Tenant identity comes from a verified Clerk session JWT. Tenant data isolation is **application-level only** — there is no database-level Row-Level Security. This was a deliberate simplicity trade-off, not an oversight.

## Commands

```bash
npm run start:dev              # watch-mode dev server
npm run build                  # compile to dist/
npm run start:prod             # run compiled build (node dist/main.js)
npm test                       # jest, all *.spec.ts
npm run test:watch
npx jest path/to/file.spec.ts  # single test file
npm run lint                   # eslint on src/ and test/
npm run typecheck              # tsc --noEmit

npm run prisma:generate        # regenerate Prisma Client after a schema change
npm run prisma:migrate:deploy  # apply pending migrations
npm run prisma:seed            # compiles prisma/seed.ts and runs it against DATABASE_URL
                                # (seeds system roles Owner/Admin/Operator/Viewer + permission catalog)
```

Everything reads a single `.env` file — no per-environment precedence rules. `ConfigModule`, the Prisma CLI, and `prisma/seed.ts` (a standalone script outside the Nest app) all load it directly.

The app fails fast at boot if `CLERK_ISSUER`, `CLERK_WEBHOOK_SECRET`, `CLERK_SECRET_KEY`, `DATABASE_URL`, `CREDENTIALS_ENCRYPTION_KEY` (must decode to exactly 32 bytes), `APP_BASE_URL`, `FRONTEND_URL`, `N8N_INTERNAL_TOKEN`, or `N8N_BASE_URL` is missing — these are genuine app-wide infra config, not something any deployment can reasonably run without.

**`SHOPIFY_CLIENT_ID`/`SHOPIFY_CLIENT_SECRET`/`SHOPIFY_SCOPES` and `ZOHO_CLIENT_ID`/`ZOHO_CLIENT_SECRET` are deliberately *not* on that list**, despite `ShopifyAdapter`/`ZohoInventoryAdapter` both being constructed at boot regardless (Nest builds every registered provider eagerly, whether or not a given deployment ever uses it). These are platform-level app credentials for one specific optional integration, not infra the whole app depends on — a deployment that hasn't set up Zoho yet must still boot. Both adapters read them with `config.get()`, not `getOrThrow()`, and expose `isConfigured(): boolean`; `IntegrationsService` checks it in three places — `GET /integrations` reports the provider `supported: false` instead of listing it as connectable, `initConnect` 404s the same way a genuinely-unregistered provider would, and `handleCallback` redirects to `?status=error` — so a missing credential degrades to "this one integration isn't available yet," never a boot crash or an unhandled exception mid-flow. (Originally a real incident: `ZOHO_CLIENT_ID`/`ZOHO_CLIENT_SECRET` missing from `.env` after standing up Zoho support took the *entire* backend down at boot, not just Zoho — `getOrThrow` in the adapter constructor doesn't distinguish "this one optional provider isn't configured" from "the app itself is misconfigured.") If a new OAuth-shaped provider is added later, follow this same pattern — `get()` + `isConfigured()` for its platform credentials, not `getOrThrow()` — rather than reintroducing the failure mode this fixed.

CORS (`main.ts`, `app.enableCors()`) is locked to exactly `FRONTEND_URL` — a static allow-list, not a wildcard or an echo of the request's `Origin`. Reuses `FRONTEND_URL` rather than a separate CORS-specific env var, since it already means exactly "the frontend's origin." No `credentials: true` — auth is a manually-attached `Authorization` header, not a cookie, so cross-origin cookie access was never needed.

## Architecture

### Request pipeline and tenant identity

- `ClerkTenantGuard` (`src/auth/guards/clerk-tenant.guard.ts`) is registered globally via `APP_GUARD` in `AuthModule` — it runs on every request unless the route/controller is marked `@Public()`. It is the **only** source of tenant/user identity in the app:
  1. Verifies the `Authorization: Bearer` session JWT against Clerk's JWKS (`ClerkVerifierService`, using `jose`'s remote JWKS resolver).
  2. Requires an `X-Workspace-Id` header and checks it matches the JWT's `org_id` claim exactly (400 on mismatch or if missing) — the header is a client-supplied hint only, never trusted alone.
  3. Resolves the Clerk org (`org_id`) to an internal `Tenant` row (403 if unprovisioned or not `ACTIVE`) and the Clerk user (`sub`) to an internal `User` row (403 if not provisioned yet — Clerk's `user.created` webhook can lag behind the session token being issued; this is a real race, not just defensive code).
  4. Stores `tenantId` / `userId` / `clerkOrgId` / `clerkUserId` / `orgRole` / `orgSlug` into request-scoped context via `nestjs-cls` (`TenantClsStore`).
- `PermissionsGuard` (`src/auth/guards/permissions.guard.ts`) is also registered globally via `APP_GUARD`, **after** `ClerkTenantGuard` in `AuthModule`'s provider array (order matters — it reads `tenantId`/`userId` from CLS, which only exist once `ClerkTenantGuard` has run). It's a no-op unless the route/controller has `@RequirePermission('resource:action')` (`src/auth/decorators/require-permission.decorator.ts`): looks up the caller's `TenantMembership` for the current tenant, checks their role's `RolePermission` set (from the seeded catalog — `prisma/seed.ts`) for the required key, 403 if missing or the membership isn't `ACTIVE`. A route with no `@RequirePermission` stays open to any active tenant member, same as before this guard existed — it only ever narrows access.
- `@Public()` (`src/common/decorators/public.decorator.ts`) exempts a route or whole controller from **both** guards above. Used by `/health`, `POST /webhooks/clerk`, `POST /webhooks/shopify/:integrationId`, and the whole `InternalController` (`/internal/*`), all of which authenticate via a different mechanism (no Clerk session on those calls).
- `InternalAuthGuard` (`src/internal/guards/internal-auth.guard.ts`) is the auth for `/internal/*` — a machine caller (n8n) holding a shared secret, not a Clerk session or tenant identity at all. Checks `Authorization: Bearer <N8N_INTERNAL_TOKEN>` with a constant-time comparison, 401 on anything else. Registered per-controller via `@UseGuards()` on `InternalController`, not as a second global `APP_GUARD` — it should never run on routes `ClerkTenantGuard` already covers.
- `@CurrentTenant()` / `@CurrentUser()` / `@CurrentUserId()` (`src/common/decorators/`) read `tenantId` / `clerkUserId` / the internal `userId` back out of CLS in controllers/services — this is how downstream code gets identity without re-deriving it. `CurrentUser` is the Clerk id (for calls back out to Clerk's API); `CurrentUserId` is the internal `User.id` (for writing an actor into our own tables, e.g. `AuditLog.userId`).

### Tenant isolation — read this before touching any query

There is **no database-level check**. A Prisma query that omits `tenantId` does not error — it silently returns every tenant's rows. Every tenant-scoped query must filter explicitly:

```ts
this.prisma.order.findMany({ where: { tenantId, /* ... */ } })
```

Recipient-scoped tables (e.g. `Notification`) additionally need a `userId` filter — tenant filtering alone isn't enough there. Code review is the only backstop for this; there's no RLS layer to fall back on.

### Tenant provisioning via Clerk webhooks

There is no manual "create tenant" endpoint. `POST /webhooks/clerk` (`src/webhooks/`) is what keeps `tenants`/`users`/`tenant_memberships` in sync with Clerk:

1. `ClerkWebhookController` verifies the Svix signature over the **raw** request body — `main.ts` enables `rawBody: true` specifically for this; a re-serialized `req.body` produces a different signature and always fails verification.
2. Dedupes on `svix-id` via the `webhooks_inbound` table (`WebhookInboundEvent`) — Svix redelivers on any non-2xx response, and can occasionally redeliver a succeeded event too. On a processing failure, the handler still acks 200 (the bug is ours to fix, not something a Svix retry resolves) and records `status: FAILED` as the trail to follow up on.
3. Dispatches to `ClerkWebhookService.handle()`, which handles `organization.created/updated/deleted`, `user.created/updated`, and `organizationMembership.created/updated/deleted`. Everything else is logged and ignored.
4. **Role assignment heuristic**: Clerk's built-in org roles are only `org:admin`/`org:member` — no concept of a 4-tier Owner/Admin/Operator/Viewer split. `resolveRoleName()` first checks `data.public_metadata?.appRole` (set by `MembersService` via Clerk's invitation/membership metadata — see "Member management" below) and uses it if present; only when that hint is absent does it fall back to the coarse guess: the first `org:admin` membership on a tenant is Owner, every subsequent `org:admin` is Admin, `org:member` is Operator. The fallback path is what fires for the org creator and for anyone added directly from Clerk's own dashboard rather than through this app's invite flow.
5. Organization deletion soft-cancels the tenant (`status: CANCELED`); it never hard-deletes, since orders and audit history hang off that row.

### Member management (`src/tenants/members.*`, `src/auth/clerk-backend.service.ts`)

Unlike every other membership write in this app (which flows one direction — Clerk fires a webhook, we update our DB), member management drives Clerk from our side: `ClerkBackendService` is the outbound counterpart to `ClerkVerifierService` (which only ever verifies things Clerk sent *us*), calling Clerk's Backend API directly. Requires `CLERK_SECRET_KEY`.

- `POST /tenants/me/invitations` calls Clerk's create-invitation endpoint with `public_metadata: { appRole }` — this is what lets the eventual `organizationMembership.created` webhook recover "invited as Viewer" vs "invited as Operator" (confirmed against Clerk's current API docs: invitation `public_metadata` round-trips onto the resulting membership's `publicMetadata`). No local `TenantMembership` row is written here — there's no `User` row for an invitee to reference yet; that only happens once they accept and the existing webhook handler creates it.
- `PATCH /tenants/me/members/:membershipId` and `DELETE /tenants/me/members/:membershipId` call Clerk's update/remove-membership endpoints *and* write the local row directly (not waiting on the resulting webhook), so the caller sees the change immediately. **Order matters on the update path**: `updateMembershipMetadata()` is called before `updateMembershipRole()`, because the role change is what triggers Clerk's `organizationMembership.updated` webhook, and that webhook can only tell Operator from Viewer via the metadata hint (both are `org:member` to Clerk) — writing metadata first means the webhook never races a stale hint.
- Neither endpoint can target the tenant's Owner (`ForbiddenException`) — there is no supported path to reassign or remove Owner from this app.
- Both write to `AuditLog` — the first real usage of that table in the codebase.
- `GET /tenants/me/members` lists local `TenantMembership` rows only (gated by `members:read`, granted to all four roles) — it does not merge in Clerk-side pending invitations, since a still-pending invitee has no local row to represent them.

### Third-party integrations (`src/integrations/`, `src/credentials/`)

`CredentialsService` (AES-256-GCM) encrypts everything before it touches `IntegrationCredential`. Every `encrypt()`/`decrypt()` call takes an `aad` parameter, always the credential's `integrationId` — that table has no `tenantId` column by design (isolation is via the `integrationId` FK join), so AAD binding means a ciphertext/iv/authTag triple copied or swapped between rows fails to decrypt instead of silently succeeding against the wrong one. The key is validated in `onModuleInit` (fail fast at boot), not lazily on first use.

One `IntegrationAdapter` per provider (`src/integrations/adapters/`), resolved via `IntegrationAdapterRegistry` keyed by `IntegrationProvider`. Adapters only talk to the third party — no Prisma access; `IntegrationsService` owns all DB writes and status transitions (same split as `ClerkVerifierService`/`ClerkTenantGuard`). Two adapter shapes: `OAuthAdapter` (Shopify, Zoho Inventory) and `ApiKeyAdapter` (Resend, EasyPost, Slack). `initConnect`/`handleCallback` dispatch on `adapter.authType`, not a hardcoded provider name — adding a provider means implementing the interface, not editing a name-check branch (see "Phase 3 adapters" below for the one place that's still an explicit per-provider switch, and why).

**Multi-value credentials** — `IntegrationCredential` still stores exactly one opaque ciphertext per integration; a provider needing more than one *secret* value serializes its own shape into that single string, never `CredentialsService` or `IntegrationsService`. Concretely: `ZohoInventoryAdapter.exchangeCodeForToken()`/`refreshToken()` return `JSON.stringify({accessToken, refreshToken, expiresAt})` (`initConnect`'s api_key/OAuth branches never JSON-parse this themselves — only the owning adapter does). Shopify's stored format is untouched (bare access-token string) — this must never change, since already-encrypted rows would fail to decrypt correctly against a reshaped expectation. **Non-secret per-provider data goes in `Integration.config` instead of the encrypted blob** — e.g. `EasyPostAdapter`'s single API-key credential is a bare string, but its required `from_address` (no secret component) is collected once at connect time and stored in `config.fromAddress` (`parseApiKeyConnectInput`'s optional `config` return value, `initConnect`'s api_key branch persists it), the same non-secret-config precedent as Shopify's `config.shop`.

**Zoho token refresh — lazy, on-demand, in `IntegrationActionsService`, not the adapter.** Adapters have no Prisma access, so the "refresh, re-encrypt, retry" sequence can't live in `ZohoInventoryAdapter.checkInventory()` itself: on a 401 it throws `UnauthorizedException` (not `BadGatewayException`, which every other upstream failure uses) specifically so `IntegrationActionsService.checkInventory()` can catch *exactly* that, call `adapter.refreshToken()`, persist the new pair via `IntegrationsService.updateCredential()`, and retry once. That `instanceof UnauthorizedException` catch is scoped to this one call path — a stray 401 from EasyPost/Slack/Shopify's own action methods must never trigger a Zoho-shaped refresh. No scheduled/proactive refresh job (no BullMQ) — the backend owns every Zoho call synchronously already, so there's no window where a stale token sits unused.

**Phase 3 adapters (Zoho Inventory, EasyPost, Slack) and Shopify's `updateOrder`** — added so the pipeline can run inventory-check → shipment-creation → Shopify-writeback → Slack-notify, all behind `src/internal/integration-actions.controller.ts` (see "Orchestrator callbacks" below), never touching an `Order`/`WorkflowRun` write directly (that's the separate bookkeeping endpoints n8n calls next). Zoho's OAuth callback is a genuinely parallel branch inside `handleCallback` (not shared with Shopify's) — it has no HMAC-over-querystring scheme, no shop-equivalent mismatch/collision check, and resolves an `organization_id` via `ZohoInventoryAdapter.fetchDefaultOrganizationId()` right after token exchange (Zoho accounts can hold multiple organizations; this app connects the first one, same single-tenant-per-integration assumption made everywhere else).

**Circuit breakers (Phase 4), `src/common/circuit-breaker/`** — `CircuitBreakerService` wraps every outbound third-party call made from `IntegrationActionsService`'s four action methods and `IntegrationsService.test()` in an [`opossum`](https://www.npmjs.com/package/opossum) breaker, one instance per `IntegrationProvider`, held for the life of the process (in-memory, no Redis — same "right amount of infrastructure for current scale" call already made for `RealtimeService`'s plain `EventEmitter`). Registered as a `@Global()` module (`CircuitBreakerModule`, same precedent as `PrismaModule`) so breaker state is genuinely shared across every call to a given provider, not re-created per request. Thresholds: 5 consecutive failures / 30s reset for Zoho, EasyPost, and Shopify; 8 consecutive failures / 15s reset for Slack (already best-effort by design, see above — a shorter cooldown and higher tolerance both match that). Implemented as `errorThresholdPercentage: 99` + `volumeThreshold: N` rather than a literal counter (opossum has no "consecutive failures" primitive) — 100 doesn't work here, since opossum only opens when the error rate *exceeds* the threshold and the rate can never exceed 100. When a breaker is open, `CircuitBreakerService.fire()` catches opossum's `EOPENBREAKER`-coded rejection and re-throws `CircuitOpenException` (`src/common/circuit-breaker/circuit-open.exception.ts`) — an `HttpException` whose body is `{statusCode: 503, error: "CircuitOpen", message, retryAfterMs}`. `error: "CircuitOpen"` is the literal contract the n8n and frontend Phase 4 work checks for, not a message-text match — deliberately distinct from a genuine upstream failure (still a 401/`BadGatewayException` with a real reason). In `IntegrationActionsService.checkInventory()`, a `CircuitOpenException` is not an `UnauthorizedException`, so it skips the Zoho refresh-and-retry path and propagates as-is, same as any other non-401 error. In `IntegrationsService.test()`, a `CircuitOpenException` is deliberately *not* treated like a normal test failure: it doesn't set `DEGRADED` or notify the tenant (the breaker tripping says nothing about whether this integration's own credential/webhook is healthy — a real `DEGRADED` transition means something different), only `lastCheckedAt` is updated, and the 503 is re-thrown as-is rather than wrapped in `BadGatewayException`.

**Rate limiting (Phase 4), `src/common/rate-limit/`** — built on [`@nestjs/throttler`](https://www.npmjs.com/package/@nestjs/throttler), in-memory store (`ThrottlerStorageService`, no Redis — same infra-appropriateness call as the circuit breakers above), but with two independent guards rather than one shared config, since the two caller populations are shaped differently:
- `TenantThrottlerGuard` — registered as a global `APP_GUARD` in `AuthModule`, between `ClerkTenantGuard` and `PermissionsGuard` (needs `tenantId` in CLS, which only `ClerkTenantGuard` populates; runs before `PermissionsGuard` so a throttled caller fails fast before that guard's membership/permission DB lookup). Keyed by `tenantId` from CLS, not `req.ip` — the thing worth protecting is one noisy tenant, not one noisy IP behind a shared NAT. 100 requests/minute. `shouldSkip()` returns true whenever CLS has no `tenantId` — every `@Public()` route (health, both webhook controllers, all of `/internal/*`) never populates it, so this guard silently no-ops on all of them without needing a decorator on each one; `InternalThrottlerGuard` covers `/internal/*` separately.
- `InternalThrottlerGuard` — applied per-controller (`@UseGuards(InternalAuthGuard, InternalThrottlerGuard)` on both `InternalController` and `IntegrationActionsController`), not a global guard, same reasoning as `InternalAuthGuard` itself: it must only ever run on `/internal/*`. `getTracker()` returns a fixed constant, not anything derived from the request — n8n's calls carry no per-tenant auth context beyond a body field, so this is one shared budget per deployment (300 requests/minute), protecting against a runaway workflow loop rather than any one tenant. Both controllers share the same guard *instance* (registered once in `InternalModule`'s providers), but `@nestjs/throttler`'s default key generation still includes the controller/handler name, so the 300/minute budget is actually per-route, not one pool split across every `/internal/*` endpoint combined — confirmed live: hitting `/internal/workflow-runs` 300 times in a row 429s on the 301st, while `/internal/ai/validate-order` is completely unaffected. The circuit breakers' per-provider approximation and this per-route reading of "300/minute across all tenants combined" are the same kind of pragmatic call — see the circuit-breaker note above.

Both guards throw `TooManyRequestsException` (`src/common/rate-limit/too-many-requests.exception.ts`) — `{statusCode: 429, error: "TooManyRequests", message, retryAfterMs}`, `retryAfterMs` in milliseconds, same structured-error-contract shape as `CircuitOpenException`. Each throttler config is deliberately named `'default'`, not something more descriptive like `'tenant'`/`'internal'` — `@nestjs/throttler` only leaves the `Retry-After`/`X-RateLimit-*` headers it sets unsuffixed when the throttler's own `name` is exactly `'default'`; anything else gets appended as `Retry-After-<name>`, which isn't the plain header the contract promises. Both `TenantThrottlerGuard` and `InternalThrottlerGuard` extend `ThrottlerGuard` with an extra constructor parameter (`ClsService` for the tenant guard) — this requires explicitly redeclaring `@InjectThrottlerStorage()`/`@Inject(Reflector)` on *every* constructor parameter position the base class also decorates, not just the ones actually being changed. `@nestjs/common`'s `Inject()` reads a class's self-declared-deps metadata via `Reflect.getMetadata` (which walks the prototype chain) before appending to it, so decorating only the storage parameter still leaves the *inherited* "inject `ThrottlerStorage`" entry sitting at the base class's `reflector` parameter position, silently resolving the subclass's own `reflector` argument to the storage service instead — surfaces at runtime as `this.reflector.getAllAndOverride is not a function`, not a compile error. Each module providing one of these guards binds `ThrottlerStorageService` to `@nestjs/throttler`'s own DI token (`{ provide: getStorageToken(), useClass: ThrottlerStorageService }`), not the bare class — `@InjectThrottlerStorage()` resolves by that token, not by type.

**EasyPost (replaced ShipStation)** — `EasyPostAdapter.createShipment()` creates the shipment, then buys the *cheapest* of the rates EasyPost returns (`rates[].rate`, parsed as a float and compared) rather than a hardcoded carrier — real rate-shopping is native to EasyPost's model, unlike ShipStation's account-level fixed-carrier setup this replaced. Every shipment still uses a fixed placeholder parcel (`{weight: 16}` oz) — no per-order package-dimensions capture exists anywhere in this app, so this is a documented simplification, not a bug; revisit once real package data is captured upstream. Unlike ShipStation (whose default "ship from" warehouse lived in its own dashboard), EasyPost requires an explicit `from_address` on every shipment request — collected once at connect time (`ConnectEasyPostSchema`'s `fromAddress`) and stored in `Integration.config.fromAddress` (see "Multi-value credentials" above), not re-asked per shipment. `IntegrationProvider.SHIPSTATION` was renamed to `EASYPOST` via `ALTER TYPE ... RENAME VALUE` (see `prisma/migrations/20260716170222_replace_shipstation_with_easypost/`) rather than a drop-and-recreate — safe here since zero rows used the old value at migration time, but this is an in-place catalog rename, not a data migration, so don't reach for it if old values are still in use.

**OAuth state** (Shopify and Zoho both): `Integration.oauthState`/`oauthStateExpiresAt` are dedicated, unique-constrained columns — not stashed in the `config` JSON. Each provider's callback (`@Public()` — the redirect carries no Clerk session) resolves *which tenant* purely from this value via the shared private `resolveIntegrationByState()` helper, so it needs a real uniqueness guarantee and an indexed lookup, not a JSON scan. Cleared (`null`) on completion so a replayed hit on the callback URL can't re-run the exchange against an already-active integration.

**Callback failure handling** (`IntegrationsService.handleCallback`) — every branch sets an explicit status, not just the success path:
- Invalid HMAC / missing query params → redirect `?status=error`, no row to write to yet.
- Unknown/expired `state`, shop mismatch vs. what was stored at connect time, or another tenant already holding this same shop `ACTIVE` → integration → `ERROR` + `lastErrorMessage`, redirect `?status=error`.
- Token exchange fails → `ERROR`.
- **Webhook registration fails after a successful token exchange → `DEGRADED`, not `ERROR` or `ACTIVE`** — the credential is genuinely valid and stored, so this is the sharpest edge case: without it, the integration would read `ACTIVE` while silently never receiving any order.

**`POST /integrations/:provider/test` clearing `DEGRADED`** — `ShopifyAdapter.testConnection` doesn't just re-check `shop.json`; it also re-fetches the stored `shopifyWebhookId` via `GET /admin/api/{version}/webhooks/{id}.json` (still read-only — `test` stays side-effect-free). `IntegrationsService.test()` only resets `status` to `ACTIVE` on a fully successful `testConnection`. This matters because a `DEGRADED` integration has no `shopifyWebhookId` in `config` (that's what failed to get set) — `testConnection` throws every time until a real disconnect/reconnect actually registers a webhook, so a passing credential check alone can never mask a still-missing webhook subscription. Don't change one half of this (the webhook check in the adapter, or the DEGRADED→ACTIVE reset in the service) without the other — they were added together specifically to keep that guarantee intact.

**Shopify order webhook** — `POST /webhooks/shopify/:integrationId` (`src/webhooks/shopify-webhook.controller.ts`, `@Public()`), path-scoped by `Integration.id` rather than one shared URL. Shopify's webhook HMAC is signed with the app's client secret (shared across every tenant's shop), so it can't identify *which* tenant on its own — a primary-key path lookup is the indexed way to resolve that instead of scanning every tenant's stored shop domain on every order. Lookup-miss, not-`ACTIVE`, or a shop-header mismatch all ACK 200 + record `WebhookInboundEvent(status: FAILED)`, never a 500 — Shopify retries a non-2xx indefinitely. On success, `ShopifyWebhookService.handleOrderCreated` returns the `Order` it wrote, and the controller immediately calls `N8nOrchestratorService.startOrderValidationRun()` (see "Orchestrator callbacks" below) with a fresh `correlationId` — this is what actually starts the order-validation workflow; a failed trigger call is treated the same as a failed DB write (the `WebhookInboundEvent` row still lands `FAILED`), since an order that never reaches n8n would otherwise sit at `RECEIVED` forever with no signal to follow up on.

**Two separate HMAC verifiers, deliberately not shared** (`src/integrations/adapters/shopify-hmac.util.ts`): `verifyShopifyOAuthHmac` (sorted query string, hex) for the callback, `verifyShopifyWebhookHmac` (raw body buffer, base64) for the webhook. Copy-pasting one onto the other's call site is an easy, silent bug.

**Resend has no email-sending endpoint.** Resend requires a verified sending domain before any mail can go out at all — there's no sandbox sender that bypasses that. `connect`/`test` are both just a read-only `GET https://api.resend.com/domains` call to validate the key.

`GET /integrations` returns the full `IntegrationProvider` catalog **except `OPENAI`** (platform-level, not tenant-facing) with a `supported: boolean` flag — `SHOPIFY`/`RESEND`/`ZOHO_INVENTORY`/`EASYPOST`/`SLACK` all have adapters registered as of Phase 3.

### Data model (`prisma/schema.prisma`)

- **Tenant / User / TenantMembership / Role / Permission / RolePermission** — RBAC. Roles can be system-wide (`tenantId: null`, `isSystem: true`, seeded) or tenant-specific.
- **Integration / IntegrationCredential** — one row per `(tenantId, provider)`. Credentials are a separate table by design: non-secret `Integration.config` can be freely queried/joined/logged without any code path touching the ciphertext in `IntegrationCredential`. `displayHint` is written once at credential-set time (e.g. `sk_live_••••1234`) — it is never derived by decrypting on read. `Integration.oauthState`/`oauthStateExpiresAt` are dedicated columns for the OAuth connect→callback round trip (see "Third-party integrations" above) — don't reuse `config` for CSRF state.
- **WebhookInboundEvent** — generic inbound webhook log (Shopify, Clerk, Slack, n8n), keyed by `(source, externalId)` for dedup.
- **Order / OrderEvent / WorkflowRun / WorkflowRunStep** — order lifecycle plus workflow execution. `OrderEvent` is an append-only audit timeline (drives the dashboard's per-order history); `WorkflowRunStep` is a *mutable* current-state projection per named step (e.g. `validate_order`, `check_inventory`, `create_shipment`) — addressable individually so a single failed step can retry without re-running the whole workflow. Don't conflate the two: events are history, steps are current state. **As of Phase 3**, `POST /internal/workflow-runs/:id/steps` (`InternalService.upsertWorkflowRunStep`) is the first real writer — `label`/`sequence` come from a static `STEP_DEFINITIONS` map keyed by `stepKey` (`src/internal/dto/create-workflow-run-step.schema.ts`), not the request body, so ordering stays stable across retries; upserts on `@@unique([workflowRunId, stepKey])`, incrementing `attempt` on repeat calls for the same step. `WorkflowRun.correlationId` is set at creation time by the orchestrator (n8n) from a value the backend already generated for its own order-processing logs — kept as-is, not regenerated, so one order's activity traces across both repos independent of n8n's own execution id. `OrderStatus` includes `VALIDATED`/`VALIDATION_FAILED` (distinct from the in-progress `VALIDATING`) — driven by `PATCH /internal/orders/:id/status`. **Decided in Phase 2**: `WorkflowRun.workflowName` stays a free-form string, not backed by a normalized entity — there's exactly one workflow (order-validation) and no near-term plan for a second, per the n8n repo's own scope (one workflow, parameterized by tenant). Revisit only if a second, genuinely different workflow shape is added.
- **Notification** — `type` is a free-form string (not an enum) so new notification kinds don't need a migration; same reasoning applies to `OrderEvent.eventType`. As of Phase 2, `NotificationsService.notifyTenant()` (`src/notifications/`) is the only writer — see "Notifications" above for its fan-out semantics and triggers.
- **AuditLog** — tenant + optional user + action/resource metadata.

Column names are `snake_case` in Postgres (`@map`/`@@map` throughout); Prisma Client fields stay `camelCase`.

### Orchestrator callbacks (`src/internal/`)

`automation-experience-center-n8n` is a separate repo/service that runs the actual order-validation workflow: the backend kicks off a run (`POST ${N8N_BASE_URL}/webhook/order-received`, Header Auth with the same shared secret as below), and n8n calls back into this backend's `/internal/*` API for everything that needs state or a secret — n8n itself never touches Postgres or holds an OpenAI key.

- `N8nOrchestratorService` (`src/internal/n8n-orchestrator.service.ts`) is the outbound half of this boundary — the one call that goes backend → n8n, mirrored against every other call in this section going n8n → backend. Exported from `InternalModule` and consumed by `WebhooksModule` (which imports `InternalModule` for it) — same shape as `AuthModule` exporting `ClerkBackendService` for `TenantsModule` to consume. Called from `ShopifyWebhookController` right after `handleOrderCreated` succeeds, with a `correlationId` generated fresh per attempt (`randomUUID()`).
- Auth is `InternalAuthGuard` (see "Request pipeline" above), not Clerk — `N8N_INTERNAL_TOKEN` is the one shared secret authenticating calls in both directions (backend → n8n webhook, n8n → `/internal/*`).
- `InternalService` (`src/internal/internal.service.ts`) owns the Prisma writes for the generic order/run bookkeeping endpoints below. `AiValidationService` (`src/internal/ai-validation.service.ts`) is split out separately (same reasoning as the integration adapters: one thing owns the third-party call) — it fetches the `Order` itself and is meant to call OpenAI directly so n8n never holds that key. **Currently mocked**: real usage needs a paid OpenAI key, so `validateOrder()` just runs a plain sanity check (has a customer email, a positive total) instead of an actual model call, returning the same `{ valid, notes? }` shape n8n already expects. Swap the method body for a real OpenAI call once billing is set up — no other file needs to change.
- Most of these endpoints take no `tenantId` (matching the n8n workflow's actual request bodies) — safe without it because `id` is a globally-unique cuid primary key, not a per-tenant sequential id, same precedent as `ShopifyWebhookController`'s `Integration.id` lookup. `workflow-runs` create and `ai/validate-order` do get `tenantId` in the body and filter by it like any other tenant-scoped query.
- Wire-format status strings from n8n (`"validated"`/`"validation_failed"`/`"inventory_checked"`/`"shipment_created"`/`"fulfilled"`/`"notified"`/`"failed"`, `"completed"`/`"failed"` on the workflow-run side, `"succeeded"`/`"failed"`/`"skipped"` on the step side) are lowercase and don't match the Prisma enums' own casing/naming (`OrderStatus.VALIDATED`/etc., `WorkflowRunStatus.SUCCEEDED`/`FAILED`, `WorkflowStepStatus.SUCCEEDED`/`FAILED`/`SKIPPED`) — each DTO schema documents the mapping at the point it happens (`ORDER_STATUS_BY_WIRE_VALUE`/`WORKFLOW_STEP_STATUS_BY_WIRE_VALUE` in `internal.service.ts`), don't assume the wire value is usable as-is elsewhere. `completed` (`OrderStatus.COMPLETED`) is deliberately absent from the order-status wire enum — only reachable via the tenant-facing `PATCH /orders/:id/status` (human override), never the automated pipeline.
- `POST /internal/orders/:id/events` isn't called by the current workflow yet — built alongside the rest so it's ready when the workflow grows more steps (per the n8n repo's integration spec).
- **Integration action endpoints (Phase 3), `src/internal/integration-actions.controller.ts` + `.service.ts`** — a *separate* controller from `InternalController`, same guard/auth, shaped around the *provider* rather than the workflow: `POST /internal/integrations/:provider/:action`, not e.g. `POST /internal/orders/:id/check-inventory`. This is "n8n orchestrates, NestJS integrates" — n8n never holds a Zoho/EasyPost/Slack/Shopify credential, every third-party call happens here. `IntegrationActionsService` reads `Order` directly (same precedent as `InternalService` doing its own `Order` queries rather than depending on `OrdersService`) for input data (line items, shipping address, out of `Order.rawPayload`) but never writes `Order.status`/`WorkflowRunStep` itself — n8n calls the bookkeeping endpoints above separately with the outcome. `InternalModule` imports `IntegrationsModule` for this (one-directional — `IntegrationsModule` doesn't import back).
- Not built yet, and never will be: `GET /internal/tenants/:id/integrations/:provider/credentials` (JIT credential fetch) — the whole point of the action-endpoint design above is that n8n stays credential-free permanently, not just until this was built.

### Realtime updates (`src/realtime/`)

Two SSE endpoints — `GET /workflow-runs/:id/stream` and `GET /tenants/:id/activity/stream` — are backed by a single `RealtimeService` wrapping a plain Node `EventEmitter` (no Redis/BullMQ; single-instance backend, the right amount of infrastructure for current scale). Every tenant-relevant mutation (`WorkflowRun` create/status-change in `InternalService`, `Order` status-change in `InternalService`/`OrdersService`, new-order creation in `ShopifyWebhookController`) calls `publishWorkflowRunUpdate`/`publishOrderUpdate`; both SSE routes subscribe via rxjs's `fromEvent` and filter by `tenantId`/`runId`. `GET /tenants/:id/activity/stream` takes a client-supplied `:id` only because the path was locked by the frontend handoff contract — every other route on `TenantsController` is CLS-derived (`me`); the handler explicitly 403s if `:id` doesn't match the caller's own tenant. The frontend's SSE client uses `fetchEventSource` rather than native `EventSource` specifically so it can attach the same `Authorization`/`X-Workspace-Id` headers as any other request — both routes stay behind the normal global guards, no separate auth path.

### Notifications (`src/notifications/`)

`GET /notifications` / `PATCH /notifications/:id/read` are the first code to read or write the previously-unused `Notification` model (see "Data model" below). No `@RequirePermission` on either route — open to any active tenant member, same as any route with no permission decorator. `NotificationsService.notifyTenant()` fans out one row per currently-`ACTIVE` `TenantMembership` in the tenant — there's no more targeted recipient concept in the schema, and both trigger sources are tenant-wide problems: a `WorkflowRun` reaching `FAILED` (hooked into `InternalService.updateWorkflowRun`) and an `Integration` reaching `DEGRADED`/`ERROR` (hooked into the three status-write sites in `IntegrationsService`). Kept to these two triggers deliberately — this surfaces real, already-detected failures, not a general-purpose event log.

### Module wiring

`AppModule` composes: `ConfigModule` (global), `ClsModule` (global, `middleware: { mount: true }`), `PrismaModule`, `CircuitBreakerModule` (global, Phase 4 — see "Circuit breakers" above), `AuthModule`, `HealthModule`, `TenantsModule`, `IntegrationsModule`, `OrdersModule`, `WorkflowRunsModule`, `NotificationsModule`, `WebhooksModule`, `InternalModule`. `PrismaService` (`src/prisma/prisma.service.ts`) is a single Nest-lifecycle-managed `PrismaClient` shared everywhere — there is one DB connection for the whole app, not per-request. `TenantsModule` additionally imports `AuthModule` (for `ClerkBackendService`, used by `MembersService`), and `WebhooksModule` additionally imports `InternalModule` (for `N8nOrchestratorService`, used by `ShopifyWebhookController`) — safe to import a second time since Nest treats a statically-imported module as a singleton across the whole graph, so neither module's providers are ever instantiated twice. Same reasoning covers the two newer leaf modules: `RealtimeModule` is imported by `OrdersModule`, `WorkflowRunsModule`, `WebhooksModule`, `InternalModule`, and `TenantsModule` (each publishes or subscribes to SSE events); `NotificationsModule` is imported by `InternalModule` and `IntegrationsModule` (each raises tenant-wide notifications on a failure transition it already detects). **As of Phase 3**, `InternalModule` also imports `IntegrationsModule` (for `IntegrationsService` — adapter lookup + credential fetch/update, used by the new `IntegrationActionsController`/`Service`) — one-directional, `IntegrationsModule` imports neither `InternalModule` nor anything that does. **As of Phase 4**, the two rate-limiting guards (see "Rate limiting" above) aren't their own module — unlike `CircuitBreakerModule`, they don't need to be globally shared, so `TenantThrottlerGuard` is a plain provider in `AuthModule` (registered as a third global `APP_GUARD`) and `InternalThrottlerGuard` is a plain provider in `InternalModule` (applied via `@UseGuards()` on its two controllers), each module binding its own `ThrottlerStorageService` instance to `@nestjs/throttler`'s DI token.

## Coding Conventions

### Import order

Separate each group below with a blank line — never let two groups run together unseparated:

```ts
// 1. Node.js builtins
import { randomUUID } from 'crypto';

// 2. NestJS (@nestjs/*)
import { Injectable } from '@nestjs/common';

// 3. Third-party (prisma, jose, svix, nestjs-cls, zod — validation)
import { z } from 'zod';

// 4. Prisma (PrismaService, generated @prisma/client types)
import { PrismaService } from '../prisma/prisma.service';

// 5. Auth (guards, verifiers — src/auth)
import { ClerkTenantGuard } from '../auth/guards/clerk-tenant.guard';

// 6. Common (decorators, CLS context — src/common)
import { CurrentTenant } from '../common/decorators/current-tenant.decorator';

// 7. Domain modules (services → controllers, e.g. src/tenants, src/webhooks)
import { TenantsService } from '../tenants/tenants.service';

// 8. Local types / DTOs (relative, same-feature-folder imports)
import { CreateOrderDto } from './dto/create-order.dto';
```

`zod` is this repo's validation layer, replacing `class-validator` / `class-transformer` (removed — nothing uses them, no global `ValidationPipe` in `main.ts`) — group it with third-party, not with Prisma or domain code.

### Validation

Per-route, not global: `@Body(new ZodValidationPipe(SomeSchema)) body: SomeInput` (`src/common/pipes/zod-validation.pipe.ts`). Failed validation → 400 with the zod issue messages. Schema + inferred type live together in `src/<feature>/dto/*.schema.ts` (e.g. `src/tenants/dto/update-tenant.schema.ts`), exporting both the `z.object(...)` and its `z.infer<>` type. This is the only validation pattern in the repo — don't reach for `class-validator` decorators or DTO classes.

## Known routes

- `GET /health` — public
- `POST /webhooks/clerk` — public, verified via Svix signature
- `GET /tenants/me` — requires `Authorization: Bearer <Clerk session token>` and `X-Workspace-Id` matching the token's `org_id`
- `PATCH /tenants/me` — same auth as above, plus `@RequirePermission('tenant:manage')` (Owner only, by the seeded role/permission matrix). Body validated by `UpdateTenantSchema`.
- `GET /tenants/me/members` — `members:read` (granted to all four roles). Lists local `TenantMembership` rows only.
- `POST /tenants/me/invitations` — `members:manage`. Body `{ email, role }`, `role` one of `Admin`/`Operator`/`Viewer` (not `Owner`). Calls Clerk's invitation API; no local row written until the invitee accepts (existing Clerk webhook handles that).
- `PATCH /tenants/me/members/:membershipId` — `members:manage`. Body `{ role }`, same restriction as above. Syncs Clerk then the local row; 403 if the target is the Owner.
- `DELETE /tenants/me/members/:membershipId` — `members:manage`. Syncs Clerk then marks the local row `REMOVED`; 403 if the target is the Owner.
- `GET /integrations` — `integrations:read`. Full `IntegrationProvider` catalog except `OPENAI`, with per-tenant status.
- `POST /integrations/:provider/connect` — `integrations:manage`. Shopify: `{shop}` → `{authorizeUrl}`. Zoho: `{}` → `{authorizeUrl}` (no per-tenant input needed). Resend: `{apiKey}`. EasyPost: `{apiKey, fromAddress}` (`fromAddress` stored in `Integration.config`, not encrypted). Slack: `{webhookUrl}` — the last three validate + store immediately (no OAuth redirect).
- `GET /integrations/:provider/callback` — public, Shopify or Zoho. Shopify verifies its own HMAC; Zoho verifies only `state` (no HMAC scheme, no shop-equivalent mismatch check). Redirects to `${FRONTEND_URL}/{tenantSlug}/integrations/{shopify,zoho_inventory}?status=success|error`.
- `POST /integrations/:provider/test` — `integrations:test`. Read-only connectivity check, never side-effecting.
- `DELETE /integrations/:provider` — `integrations:manage`. Best-effort third-party cleanup, then deletes the row.
- `POST /webhooks/shopify/:integrationId` — public, verified via Shopify's webhook HMAC (base64/raw-body — a different verifier from the OAuth callback's hex/query-string one).
- `GET /orders`, `GET /orders/:id`, `GET /orders/:id/timeline`, `GET /workflow-runs`, `GET /workflow-runs/:id` — all `orders:read`.
- `PATCH /orders/:id/status` — `orders:write`. A human override, distinct from the internal n8n-only status write. Body `{ status: "FULFILLED"|"NOTIFIED"|"COMPLETED"|"CANCELED", reason?: string }` — restricted to the terminal/manual-intervention statuses, not the automated pipeline's own internal ones (e.g. `VALIDATING`). Writes an `OrderEvent` (`manual_override`) and an `AuditLog` row atomically, then publishes a realtime order update.
- `POST /workflow-runs/:id/retry` — `orders:write`. 202. Only a `FAILED` run with an associated order can be retried; re-invokes `N8nOrchestratorService` the same way a new Shopify order does, with a fresh `correlationId`. Does not mutate the existing run row — n8n creates a new `WorkflowRun` on restart via `POST /internal/workflow-runs`.
- `GET /notifications` — no permission required (open to any active tenant member). Paginated (`take`/`skip` query params), tenant- and user-scoped, includes `unreadCount`.
- `PATCH /notifications/:id/read` — no permission required. Sets `readAt`; 404 if the notification isn't the caller's own.
- `GET /workflow-runs/:id/stream` — `orders:read`. SSE, one run's status changes.
- `GET /tenants/:id/activity/stream` — `orders:read`. SSE, tenant-wide feed (new orders + workflow run status changes); 403 if `:id` doesn't match the caller's own tenant.
- `POST /internal/workflow-runs` — public route, `InternalAuthGuard` (shared-secret bearer). Body `{ tenantId, orderId, correlationId }`, 201 → `{ workflowRunId }`.
- `POST /internal/ai/validate-order` — same guard. Body `{ tenantId, orderId }` → `{ valid, notes? }`; mocked pending a paid OpenAI key (see "Orchestrator callbacks" above).
- `PATCH /internal/orders/:id/status` — same guard. Body `{ status: "validated" | "validation_failed" | "inventory_checked" | "shipment_created" | "fulfilled" | "notified" | "failed", reason?: string }`. `reason` is only meaningful with `"failed"` — recorded as an `order_failed` `OrderEvent`. Response echoes `{ updated: true, status }` (the wire-format value, not the Prisma enum) — n8n's "Close Workflow Run" node branches on this.
- `PATCH /internal/workflow-runs/:id` — same guard. Body `{ status: "completed" | "failed", errorMessage? }`.
- `POST /internal/workflow-runs/:id/steps` — same guard. Body `{ stepKey, status: "succeeded"|"failed"|"skipped", error? }` — lowercase wire values, same convention as order status, mapped to `WorkflowStepStatus` in `InternalService`. `stepKey` one of the static `STEP_DEFINITIONS` keys (`validate_order`/`check_inventory`/`create_shipment`/`update_shopify`/`notify_slack`), 400 on an unknown key. Upserts `WorkflowRunStep`.
- `POST /internal/orders/:id/events` — same guard. Body `{ eventType, payload? }`; appends to the order's audit timeline. Not called by the current n8n workflow yet.
- `POST /internal/integrations/zoho/check-inventory` — same guard. Body `{ tenantId, orderId }` → `{ inStock, availableQuantity? }`. Refreshes the Zoho token once on a 401 and retries before giving up.
- `POST /internal/integrations/easypost/create-shipment` — same guard. Body `{ tenantId, orderId }` → `{ trackingNumber, carrier, shipmentId }`. Buys the cheapest rate EasyPost offers; `from_address` comes from `Integration.config.fromAddress`, `to_address` from the order's Shopify `shipping_address`.
- `POST /internal/integrations/shopify/update-order` — same guard. Body `{ tenantId, orderId, trackingNumber, carrier }` → `{ success: true }`. Writes fulfillment/tracking back to Shopify; `notify_customer: false` (customer notification is the separate Slack step, not Shopify's own fulfillment email).
- `POST /internal/integrations/slack/send-message` — same guard. Body `{ tenantId, message }` → `{ success: true }`. Best-effort by n8n's own node config, not this endpoint — a failure here is reported honestly, never swallowed.

## Troubleshooting notes worth knowing before debugging from scratch

- `Cannot find module '.../dist/main'` right after a clean "Found 0 errors" build usually means `dist/tsconfig.tsbuildinfo` is stale relative to `dist/`. The build info file lives inside `dist/` on purpose so the two can't drift; if it resurfaces, `rm -rf dist` and restart.
- A `400 Bad Request "Invalid webhook signature"` from `POST /webhooks/clerk` means either `CLERK_WEBHOOK_SECRET` doesn't match that specific endpoint's signing secret in the Clerk dashboard (each endpoint has its own), or something between Clerk and the app re-serialized the request body in transit.
- Same class of issue for `POST /webhooks/shopify/:integrationId`, but check `SHOPIFY_CLIENT_SECRET` instead, and remember the webhook HMAC and the OAuth callback HMAC are verified by two different functions with different encodings (`shopify-hmac.util.ts`) — don't assume one bug is the other.
- A Shopify integration stuck at `DEGRADED` right after connecting means the token exchange succeeded but webhook registration didn't — check `Integration.lastErrorMessage`. The credential is real; orders just won't sync until it's retried (disconnect/reconnect re-runs the whole flow).
- `DEGRADED` with `BadGatewayException: ... 403` specifically means Shopify's **Protected Customer Data** approval is missing — separate from OAuth scopes. `orders/create` carries customer PII, so beyond `read_orders` the Partner app needs explicit approval: partners.shopify.com → the app → API access requests → Protected customer data access → Request access → **Store management** (the only reason that matches what this app actually does — don't select others). Immediate on a dev store, no review needed. `shopify.adapter.ts`'s `registerWebhook` doesn't log the response body on failure, so the 403 status alone won't show this — the FE's `ShopifyProtectedDataDialog` (shown on a `DEGRADED` Shopify integration) has the step-by-step fix.
- The webhook can arrive successfully (no error anywhere) while `payload.customer` is missing `email`/`first_name`/`last_name` and top-level `payload.email` is absent too — this is a *second*, separate gate on top of the one above. Protected Customer Data access has two steps: picking a reason (unblocks the webhook subscription — the point above) and then **individually selecting which protected fields you need** (Name, Email, Phone, Address) on the same Partner Dashboard page. Skipping the field selection gets you the webhook with PII silently stripped, no error raised anywhere. Fix: partners.shopify.com → the app → API access requests → Protected customer data access → past the reason picker → check **Name** and **Email** (the two fields `shopify-webhook.service.ts` reads). Confirm on the next test order via `Order.customerEmail` or the FE's `OrderValidationFailureDialog`.
- A successful "Test connection" that leaves the badge on `DEGRADED`/"Needs attention" means `ShopifyAdapter.testConnection`'s webhook re-check (see "`POST /integrations/:provider/test` clearing `DEGRADED`" above) is missing or was reverted — a plain `shop.json` check alone can't tell `IntegrationsService.test()` it's safe to restore `ACTIVE`. The actual fix for a `DEGRADED` integration is still disconnect/reconnect (that's what registers the missing webhook); `test` can only confirm health, never create the webhook itself.
- Local Shopify OAuth testing requires `APP_BASE_URL` to be a tunnel (ngrok or similar) reachable from Shopify's servers, not `localhost` — and the Partner app's redirect URI must match it exactly (`${APP_BASE_URL}/integrations/shopify/callback`). `nest start --watch` does not pick up `.env` edits (only source file changes trigger a rebuild) — a running process keeps serving whatever `APP_BASE_URL` it read at boot until restarted by hand, which can silently desync the served `redirect_uri` from both the current `.env` and the current tunnel.
- `ERROR [IntegrationsService] TypeError: fetch failed` during the Shopify callback (token exchange) is a network-level `fetch()` failure, not necessarily a config bug. Confirmed cause on this project: `*.myshopify.com` has both `A` and `AAAA` records, and a dead/non-forwarding IPv6 default route on the host makes Node's `fetch` (which prefers IPv6 via Happy Eyeballs) hang and fail against Shopify while plain IPv4-only sites still work. `main.ts` sets `dns.setDefaultResultOrder('ipv4first')` at boot to route around this — check that's still present before re-diagnosing. Verify with `dig AAAA <shop>.myshopify.com` and `curl -6` vs `curl -4` to the same host.
- `npm run lint` references `eslint`, but no `eslint` package or config is installed yet — the import-order convention above is enforced by convention/review only, not tooling, until that's set up.
- A Shopify webhook that keeps landing as `WebhookInboundEvent(status: FAILED)` even though `Order`/`OrderEvent` rows are actually being written means `N8nOrchestratorService.startOrderValidationRun()` is the thing throwing, not `handleOrderCreated` — check that n8n is actually running and reachable at `N8N_BASE_URL`, and that `N8N_INTERNAL_TOKEN` matches n8n's "Backend Internal Token" credential exactly.
